# PR/MR body template

`/pr` and `/mr` write the same structured description, so review artifacts read the same on both forges.

## Kept in sync across two skills

The template is duplicated verbatim between `/pr` and `/mr` (skills load standalone — no include mechanism), marked with `<!-- pr-body:v1 -->` and checked by `task verify:pr-body`. The marker sits below the section heading, so `## PR Body Template` and `## MR Body Template` may differ while everything from the intro line through the closing fence stays byte-identical. Edit both files and bump the marker together.

## Fence markers

The template body is wrapped in `<!-- mr-body:start -->` / `<!-- mr-body:end -->` markers that both skills write into the PR or MR description. These delimit the region the skills own: on update they rewrite only what sits between the markers, and everything outside is preserved byte-for-byte in its original position — reviewer-bot summaries such as Cursor Bugbot's, other tooling's generated blocks, and hand-written additions all survive without the skills needing to recognize them.

The rule is positional, not name-based. Neither skill knows what any particular bot is called or what its output looks like; content is preserved because of where it sits, not because it was recognized.

The markers are shared rather than forge-specific so a PR body stays recognizable if the branch moves between forges.

## Migration and edge cases

**Descriptions predating the markers** are migrated in place on the next update. The skill locates the contiguous run of template sections, replaces that run with the fenced body, and leaves surrounding content where it sits. If no template sections are found, the fenced body is inserted at the top rather than overwriting anything.

**An unpaired opener is treated as unfenced.** If a closer is deleted by hand or lost to a bad merge, reading opener-to-end-of-body would swallow everything below it. That case falls back to migration instead, which fails toward duplication rather than deletion — a duplicated line is recoverable, a deleted review comment is not.

**Content between template sections cannot stay in place.** Anything wedged inside the fenced region is part of what gets rewritten. Notes meant to survive belong outside the fence.

## The autogenerated notice

An HTML comment under the opener states that the region is autogenerated, that edits inside it are lost on the next update, and that notes belong outside the fence. It is invisible in the rendered description and plain in the edit box, which is where someone is standing when they are about to make that mistake. Updates re-emit it, so it does not disappear the first time a body is rewritten.
