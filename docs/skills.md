# Skill behaviour

Behaviour shared across skills, or too involved to leave implicit in a single `SKILL.md`. Each skill's own file remains the source of truth for how it runs; this covers the parts that span more than one, or that explain why a skill is built the way it is.

## The per-CLI agent boundary

`/pr`, `/pr-review`, `/remote-issue`, and `/remote-release` each serve every backend they support from one file, and none contains a remote command. The `gh`, `glab`, and `acli` agents own the command vocabulary — flags, JSON field names, anchor semantics, mutual exclusions — one CLI per agent, so no agent branches on backend and no skill duplicates a table. The skill picks the backend, dispatches a work order naming an operation, and the operation names are shared across agents, which is what lets one skill drive any of them.

The tables cover each CLI's ordinary surface rather than the subset a skill happens to call today, so an operation that already exists does not arrive as a one-line commit the first time something needs it. Breadth is bounded by naming, not by omission: no agent runs an operation the work order did not name, and each carries an irreversible-operation clause for the handful that cannot be undone — merging, deleting a release, removing a branch or tag, and on Jira any write scoped by a JQL query rather than a key. An order that gestures at one of those ("close this out") is reported as ambiguous rather than resolved into the destructive reading.

How the backend gets picked differs by what it is scoped to. A forge follows the code, so `/pr`, `/pr-review`, and `/remote-release` resolve it from the `origin` remote, and where a self-hosted URL settles nothing they ask each agent for `repo-id` and take the one that resolves. A tracker does not: a repo on GitHub may track its work in Jira, so `/remote-issue` asks rather than inferring from the remote — offering the forge matching `origin` as a default to confirm, not as a decision already made — and a Jira create is scoped by a project key that has nothing to do with the working directory.

Two failures stop a run outright rather than being routed around, because the alternative is a skill that quietly does the thing its rules forbid. An agent that cannot be spawned is not installed, and the skill names it. A CLI the agent cannot find is reported as its own kind of failure rather than as an auth error — `FAIL auth -- glab is not installed: <url>` — so the user gets told what to install instead of being sent to re-authenticate something absent. Neither case permits falling back to a raw CLI call from the skill, and `/remote-release` additionally refuses to tag or push toward a release it has already learned it cannot publish.

The split is invocation versus content. The agent decides how a comment is posted; the skill decides what it says — including the suggestion-block dialect, which differs by forge (`suggestion` on GitHub, `suggestion:-0+0` on GitLab) but is a property of the body, not of the command, so it stays with the skill that writes the body. Where a backend models as a field what another leaves to prose — Jira's work item type, against GitHub's `## Type` body section — that mapping is also the skill's, since it decides what the body contains.

Payloads cross the boundary as file paths, never as prose in a message. A description or a review comment has to arrive byte-exact — an anchor, a verbatim summary line, an indentation-exact suggestion block — and re-emitting it into a prompt is where an indent or a line number shifts. The skill writes the body to a temp file and passes the path; `--body-file` and `@<path>` on GitHub, `--description-file` on Jira, stdin redirection and `"$(cat …)"` on GitLab, since `glab` reads neither a description nor a note body from a file directly. The agents have no `Write` tool, so authoring a body is structurally out of reach rather than merely forbidden.

Identical operation names do not mean identical semantics, and where two CLIs fail differently the agents are configured so neither hides it. `release-create` is the sharpest case: `gh` refuses to publish against a tag missing from the remote (`--verify-tag`), while `glab` would create that tag itself from a ref and so mask a failed push — hence the skill pushes the tag before dispatching either way, and the `glab` order carries no `--ref`. In the other direction, `gh` errors when a release already exists for a tag but `glab` silently overwrites its name and notes, so the `glab` agent pins `--no-update` and the skill refuses a version that already resolves locally. Titles diverge too (`--title` against `--name`), which is precisely the sort of detail that belongs in one table per CLI rather than in a skill trying to remember both. `draft` and `ready` diverge in shape rather than in outcome — one `gh` command with an `--undo`, two `glab` flags on `mr update` — and in what can refuse them: converting to draft depends on the account's plan on GitHub, while GitLab keeps the state in a `Draft:` title prefix, so a title edit there can flip it by accident. Both are carried as operations for that reason, so no caller reaches for a title.

Command tables are transcribed from the CLI itself wherever the binary is available, which is how the mutual exclusions and the file-reading forms above were established rather than assumed. `acli` was transcribed from [Atlassian's published reference](https://developer.atlassian.com/cloud/acli/reference/commands/jira-workitem-create/) instead, so its table carries a note saying so: an unknown-flag error from `acli` means the table is wrong and wants fixing at the source, and the agent reports it verbatim rather than substituting something that looks close.

Anchors are never re-derived across the boundary. A stale head SHA means the author pushed since the review was written, and recovering from it needs the new diff — which lives in the skill, not the agent. The agents therefore report a rejected anchor and stop; retrying against a line the agent picked would put a comment on unrelated code. Reports are per item, keyed by finding number, because the skill writes a local record of what posted from them and a batch collapsed into one line corrupts it. Neither forge offers a double-post guard for anchored comments — `glab`'s `--unique` is mutually exclusive with `--file` — so an unmatched report is checked against existing threads before anything is retried.

Agents install to `~/.claude` only. On Gemini all four skills install and their backend-agnostic reasoning still applies, but the dispatch has nothing to dispatch to, the same way the SDLC skills depend on agents that platform does not receive.

## When a template moves to its own file

The rule below, and the rest of what governs how these files are written -- what earns a place in one, what is derivable and gets cut, when a constraint becomes a violation clause -- is enforced operationally by `/skill-write`. This document explains why the repo is shaped as it is; that skill applies it while editing.

A skill can ship reference files beside `SKILL.md` and read them on demand. That pays in exactly one situation: **when the context that loads the skill is not the context that uses the template.** Where they are the same, extraction buys nothing and costs a `Read` round-trip plus the chance the model skips it, so the template stays inline.

`/sdlc-design` is the one case that qualifies. Its main thread is a pure router, forbidden by its own rules from producing specs, plans, or task files — yet it was loading 110 lines of artifact templates on every invocation, while `sdlc-architect`, which does the authoring, read the whole `SKILL.md` to find them. Splitting them into `templates.md` cut the orchestrator's file by more than half and left the architect reading only what it fills in.

Everything else stays where it is, by the same rule: `/pr`'s body template, `/remote-issue`'s issue template, `/commit`'s message template, `/pr-review`'s report and comment formats, and the agents' command tables are all used by the very context that loaded them.

The architect reads `~/.claude/skills/sdlc-design/templates.md`, the installed path, which resolves from whatever project directory it is running in. It previously pointed at a repo-relative path that resolves nowhere but here, so it would have fallen back to reconstructing the format from memory — the last thing a template meant to be used verbatim should do.

## Markdown the skills write

Two skills write Markdown files into someone's repository: `/pr-review` writes `docs/pr-reviews/<number>.md`, and `/sdlc-design`'s architect writes every artifact under `plans/`. Those land where a linter may already be running, so both carry the same short rule — blank lines around headings, lists, and tables; a language on every fence; one top-level heading; no trailing whitespace; one trailing newline. It is one sentence in each, stated where the authoring happens, by the rule above: neither context reads this document at runtime.

Line length is not among them. This repo turns `MD013` off and the skills stay silent on wrapping, because the host repo owns that choice — and for a review report, rewrapping would break the summary line that posting reuses verbatim.

What a skill sends to a forge is exempt: a PR description, an issue body, and release notes are rendered by the forge and never checked out, so they follow the body templates alone. The one rule a written file cannot satisfy is `MD029`, since `/pr-review` numbers findings continuously across sections and never reuses one, making a section that opens at finding 4 an identifier rather than a miscount. The report disables that rule in its own header, where whoever reads the numbering can see why.

## PR/MR body template

`/pr` writes the same structured description on both forges, so review artifacts read the same either way. There is one copy of the template, in `skills/pr/SKILL.md`.

The template body is wrapped in `<!-- pr-body:start -->` / `<!-- pr-body:end -->` markers that the skill writes into the description. These delimit the region the skill owns: on update it rewrites only what sits between the markers, and everything outside is preserved byte-for-byte in its original position — reviewer-bot summaries such as Cursor Bugbot's, other tooling's generated blocks, and hand-written additions all survive. The rule is positional, not name-based: the skill does not know what any particular bot is called, and content is preserved because of where it sits, not because it was recognized. An HTML comment under the opener states that the region is autogenerated, so the warning reaches whoever is in the edit box.

Descriptions predating the markers are migrated in place on the next update: the skill locates the contiguous run of template sections, replaces that run with the fenced body, and leaves surrounding content where it sits. An unpaired opener is treated as unfenced rather than as a boundary, so a hand-deleted closer cannot swallow the rest of the body.

Markers are recognized on the token alone, ignoring whitespace inside the comment: `<!--pr-body:start-->` and `<!-- pr-body:start -->` are the same marker. Editors and API clients normalize HTML comments, so spacing altered in transit does not change how a body is classified. Recognition is tolerant; what the skill writes back is always the canonical spacing.

`mr-body:start` / `mr-body:end` are recognized as legacy equivalents and rewritten to the canonical token on the next update. They were what the former `/mr` wrote, and — through a template kept byte-identical across the two skills by an automated check — what the former `/pr` wrote into GitHub bodies too. Both are now `/pr`, canonical on `pr-body`, and bodies in the wild migrate as they are touched.

Markers are the fast path, not the only one. HTML comments are invisible by design, which is why Markdown pipelines and sanitizers feel free to drop them entirely — so the skill falls back to recognizing the body by its structure: a contiguous run of Tickets, Summary, Why, Changes in that order is treated as a region a previous update owned, marker or no marker, and is replaced in place. A fresh body is inserted at the top only when no template-shaped run exists anywhere. That ordering is what makes the fence self-healing rather than a single point of failure: lose the markers and the next update rebuilds them around the existing body instead of adding a second one beside it.

## PR review

`/pr-review` writes numbered findings — Should change and Could change — to `docs/pr-reviews/<number>.md` in the repo the PR or MR belongs to, checking the working directory's project against the PR/MR's first so a mistyped number cannot write into an unrelated repo. The file is left unstaged and never gitignored; whether review notes belong in a repo's history is a per-project call.

There are three modes, and local is the default. A local run writes the report and stops; comments go up only on a later instruction naming which findings to send, which is what the numbers are for. A submit run — named by `--submit` or by asking for the review to be submitted — writes the same file first, then sends the findings to the forge, so what landed has a local record to be marked on. Approve is explicit-request-only in both, never a consequence of a favourable verdict: a submit run whose verdict reads approve posts as a plain comment and says the approval is waiting to be named.

The forges do not offer the same verdicts, and the skill states the gap rather than papering over it. GitHub takes the whole review in one call — every inline comment and the event together, so it lands whole or not at all and arrives as one notification — and supports `REQUEST_CHANGES`, `COMMENT`, and `APPROVE`, but has no revoke short of a dismissal needing the review id and elevated access. GitLab has no batch and no changes-requested state at all: notes go up one at a time and approval is its own command, so a changes-needed verdict posts as a note and the state is reported unsupported. Revoking an approval is not a substitute for it, and neither agent simulates a verdict its CLI lacks.

A posted finding keeps its thread id, which is what makes the third mode possible. Submitting records `(posted <date>, thread <id>)` against each finding, and a follow-up run resolves the threads back to the report by that id — or by the `(N)` marker every posted body carries, for a review written before ids were kept. What comes back is answered with the same investigation obligation the review ran under: a reply pointing at code is checked against that code first. Replies go up only on a request naming which threads to answer, and neither mode resolves a thread — resolution is the author's signal that they acted, so the skill recommends it and leaves it to them.

Questions are investigated, not collected. Whatever the diff raises is chased as it surfaces — the callers, the definition, the tests, the history, the linked issue — in parallel with the findings rather than deferred to the end, and what the repository answers becomes a finding or nothing at all. What it cannot settle is still a finding rather than a question handed back: it routes by consequence into Should or Could change and carries its condition — what must hold, what breaks if it does not, and what was already checked — so the author confirms rather than investigates, and is asked for intent or an external system and never for what a search would have told them.

Scope is the change itself. A finding traces to a line the diff touched or to code the change makes wrong — a caller the new signature breaks, an invariant it violates, a test it leaves stale. Surrounding code is read to judge that and never mined for findings of its own, which is what keeps the review of one change from becoming an audit of the files it lands in.

Findings are written once, in one voice, for two readers: the reviewer scanning the report and the author reading a posted comment cold. Each opens with a [Conventional Comments](https://conventionalcomments.org/) summary line — `issue (blocking): the handle is never closed on the error path` — so the author sees the kind of remark and whether it blocks the merge before reading the reasoning. The report section decides the label and decoration: Should change posts as blocking, Could change as non-blocking. Beneath it the finding addresses the code rather than the person, states what was observed and what follows from it, and flags where intent was inferred. Because the report and the comment share that text verbatim, there is no rewrite step between them for tone to drift through.

Re-reviewing appends a section headed by the head SHA it was reviewed at, rather than a round counter. The revision is a fact about the review, so an already-reviewed head is detectable rather than silently duplicated, and comparing that SHA against the current head is what catches anchors gone stale because the author pushed since. Numbering continues upward across sections, so a number already posted keeps pointing at the same finding.
