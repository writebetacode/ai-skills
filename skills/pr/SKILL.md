# PR

## Workflow

Verify `gh auth status`; stop on failure. Gather in parallel: current branch, remote URL, user login, PR status. Warn on uncommitted changes. Resolve base from arguments, or auto-detect by matching branch-name prefix against other local branches, falling back to `git merge-base` against the repo's default branch — resolve it via `git symbolic-ref --short refs/remotes/origin/HEAD` (strip the leading `origin/`), or `git remote show origin` parsed for `HEAD branch:` if that ref is missing; never assume `main`, since the repo may default to `develop`, `master`, or `trunk`. Validate ticket numbers via `gh issue view`. Draft a human-readable title under 70 characters covering combined changes. Compose body from the template, run `gh pr create --assignee @me --base <base>` or, when editing an existing PR, follow the Update Path below. Add `--draft` if "draft" appears in `$ARGUMENTS`. Display the PR URL.

## Update Path

`gh pr edit --body` replaces the description wholesale, so anything already in the field is lost unless deliberately carried forward. Reviewer bots, teammates, and prior manual edits all write into that same field. You own only the fenced block; everything outside it is someone else's and must survive the update unchanged and in place.

Fetch the current body first:

```sh
gh pr view <number> --json body --jq .body
```

Then apply whichever case matches.

**Recognizing a marker.** Match markers on the token alone — `mr-body:start` and `mr-body:end` inside an HTML comment — ignoring internal whitespace entirely. `<!--mr-body:start-->`, `<!--   mr-body:start   -->`, and the canonical `<!-- mr-body:start -->` are the same marker, as is a marker carrying trailing spaces or sitting on a line with other text. Editors and API clients normalize HTML comments, so a body that round-trips through one can arrive with its spacing altered. Recognition is tolerant; what you write back is always the canonical spacing. Markers are the fast path, not the only one — a body that lost them entirely is still recognized structurally by the Unfenced rule below.

**Fenced.** The body contains both markers, opener before closer: replace everything between them with the freshly composed body, re-emitting the markers in canonical form along with the autogenerated notice beneath the opener. Every byte before the opener and after the closer stays exactly as-is, in its original position and order. Do not reorder, relocate, normalize whitespace in, or reformat any of it.

**Unfenced.** Neither marker recognized, or an opener without a matching closer: fall back to recognizing the body by its structure instead. Locate the contiguous run of template sections — Tickets, Summary, Why, Changes, and any Breaking Changes or Dependencies, in that order, starting from the first `## Tickets` heading. That run is the region a previous update owned, whether it was written before the markers existed or lost them since. Replace it in place with the fenced body, leaving surrounding content where it sits. Never treat an unpaired opener as a fence boundary; a hand-deleted closer would otherwise swallow the remainder of the body.

Structural recognition is what keeps the markers from being a single point of failure. HTML comments are invisible by design, which is why Markdown pipelines and sanitizers feel free to drop them; if that happens, the previous body is still sitting there in template shape, and matching on that shape replaces it rather than inserting a duplicate beside it. Treat a template-shaped run as owned even when no marker survives.

Insert the fenced body at the top, preserving everything else below, **only** when no template-shaped run is found at all — a genuinely new or freeform body. Never insert while a template-shaped run exists somewhere in the body: that is the one move that produces two bodies, and a second update would then compound it.

Content outside the fence is preserved by position, whoever or whatever wrote it — reviewer-bot summaries, other tooling's generated blocks, hand-written notes. Recognizing the source is never required, and no marker needs protecting by name.

Preserve everything outside the fence byte-for-byte — never reword, resummarize, reformat, or template-conform it, and never regenerate another tool's summary from the diff. When a boundary is ambiguous, prefer carrying content forward over dropping it; a duplicated line is recoverable, deleted review feedback is not. Never resolve an awkward layout by skipping the update or leaving the fenced body stale.

## PR Body Template

<!-- pr-body:v1 -->
Use this exact markdown structure, fence markers included. Omit Breaking Changes and Dependencies when not applicable. The markers delimit the region this skill owns and rewrites on update; everything outside them is preserved untouched.

```markdown
<!-- mr-body:start -->
<!-- Autogenerated. Everything inside this fence is rewritten on each update
     and any edits here will be lost. Add notes outside the fence; content
     there is preserved exactly as written. -->
## Tickets
[#<number>](<url>) — <title>, or N/A

## Summary
<2-4 sentences: what changed and why.>

## Why
<The value this delivers and the intent behind it, without detailing implementation mechanics.>

## Changes

**<Category>**
- `<file>`: <summary of change>
- `<file>`: <summary of change>

**<Category>**
- `<file>`: <summary of change>

## Breaking Changes

<Describe any breaking changes, or omit this section entirely.>

## Dependencies

<List added, removed, or upgraded dependencies, or omit this section entirely.>
<!-- mr-body:end -->
```

## Rules

Always assign to @me with `--assignee @me`. Never reference a ticket without validating it via `gh issue view` first. Restrict generated output -- commits, PRs, issues, and files you write -- to ASCII; never include AI attribution or "Co-Authored-By" lines.

**Title violation:** any title that is not a plain-English, human-readable sentence — raw branch names, ticket slugs, kebab-case, or machine-style identifiers must be rewritten before create/update. `fix/auth-token-refresh` or `PROJ-123` are violations; "Fix authentication token refresh on expired sessions" is acceptable.

**Body violation:** any body off the exact template — Tickets, Summary, Why, and Changes in that order using the prescribed markdown. Freeform prose, generic layouts, or invented sections like "Test Plan" must be corrected before create/update.

The template governs only what sits between the `mr-body` fence markers. Content outside them — a reviewer bot's summary, another tool's generated block, a teammate's hand-written section — is never a violation regardless of its shape or position. Do not trim, rewrite, relocate, or template-conform it to satisfy this rule; enforce the template on the fenced region alone.
